From the last committed **read-only** audit ([`data/production-db-baseline-audit.json`](../data/production-db-baseline-audit.json)):

- **Correct database class:** Hosted Postgres with large **`public`** catalog (legacy / warehouse / snake_case style) plus **`auth`** objects.
- **`public._prisma_migrations`:** Absent in that snapshot — Prisma migration history is **not** yet tracking this database.
- **High-value tables:** Present (voter/contact/adjacent warehouse tables enumerated in audit JSON).

## Production checksum / edited migration risk

Editing **`20260505203000_email_contact_profile_graph/migration.sql`** changes the checksum Prisma stores in **`_prisma_migrations`** for that migration name. Any environment that already recorded the **old** checksum may need a **DBA-governed** resolution path. The frozen production audit showed **no** `_prisma_migrations` table — that reduces **direct** production checksum collision risk but **not** staging/clone risk.

## Baseline options

| Id | Summary | Meaning (short) | Primary risks |
|----|---------|-----------------|---------------|
| **A** | Mark historical migrations applied | After backup + DBA review, establish `_prisma_migrations` without re-running SQL that is already true on disk. | History can **lie** if production does not actually match every migration. |
| **B** | New baseline migration package | Introspect or capture production; baseline migration; branch future app migrations from there. | **Hard** with **71** existing folders; history fork must be deliberate. |
| **C** | Separate legacy warehouse from Prisma app | Do-not-touch warehouse; Prisma owns only mapped/new app tables. | App must not treat legacy tables as Prisma-owned. |
| **D** | Controlled execution after shadow proof | Shadow **`migrate deploy`** + clean diff as evidence; then execution packet on production with backup + Steve approval. | Still needs PITR, approval, exact commands, Netlify coordination. |

Full machine-readable copy: `baselineOptions` in [`data/production-baseline-execution-review.json`](../data/production-baseline-execution-review.json).

## Recommended path

**Option D**, with **Option C** as ongoing discipline: use shadow proof as evidence, then a **single** Steve-approved **REDDIRT-PRODUCTION-BASELINE-EXECUTION-PACKET-1.0** for production alignment. Do **not** use Option A alone without proving schema equality migration-by-migration. Option B remains a **fork-the-world** strategy — only if D is blocked by organizational constraints.

See `recommendedPath` in [`data/production-baseline-execution-review.json`](../data/production-baseline-execution-review.json).

## Required human approvals

1. **Steve:** written approval for **any** production mutation (`migrate deploy`, `migrate resolve`, `db push`, `reset`, or DBA DDL batch).
2. **Steve:** explicit choice if execution packet deviates from Option D.
3. **Operator:** database **identity** confirmed against the intended Supabase project (no secret paste into tickets).
4. **Operator / DBA:** checksum audit for any DB that might have applied the **pre-edit** `20260505203000` migration.

## Required backup / PITR proof

- Supabase **PITR** enabled with documented retention **or** a **verified logical backup** plus **restore drill** on a disposable instance.
- **Rollback owner** and decision criteria before first production DDL.
- Proof artifacts stored **outside** this repo per secrets policy.
